# 停车反馈是否被使用，以及为什么仍会等待

本次低资源回放复现了新候选 **1,369 帧模型接管动作**，同时检查 eager 模型与实际导出模型、动作掩码及原始扫描质量特征一致。未新增物理试验或训练更新。

| 失败恢复段 | 基础策略建议运动、恢复头改成停止 | 仅把恢复头的上一停车原因替换为 `none` 后改变动作 |
|---|---:|---:|
| 95 秒接管 | 125 帧 | 60 帧 |
| 90 秒接管 | 225 帧 | 190 帧 |

例如 95.8 秒，原状态有 10 个合法运动动作，基础策略选择左转，恢复头停止概率约 0.9999。保持原硬掩码、支持范围和其他头输入，仅将上一帧 `policy_wait` 反馈替换为 `none`，停止概率变为约 0.0107。这表明停车反馈会影响输出；不能据此声称模型正确理解了停车原因，更不能直接执行反事实动作。

同一诊断中，距离、目标和等待时长输入的移除对该失败段多数动作影响较小。结合物理超时结果，当前线索是恢复头过度依赖“此前已停车”，形成持续等待倾向，而不是所有运动都被安全层否决。该解释仍需通过完整安全来源和新模型闭环验证。

训练数据审查还确认：2,848 条来源中，实际进入恢复头更新的 2,300 条没有动作 4（纯左转）或动作 9（小幅右弧）的正确标签；完整数据虽然有少数此类动作，它们落在冻结部分、不参与恢复头更新。已等待至少 2 秒后恢复的运动标签仅有动作 1、6、11。失败状态的基础策略却会建议动作 4、9。不能用所有动作都存在于输出空间来代替训练覆盖。

接下来的实验从已记录失败状态中，按当前观测选择第一个“至少等待 2 秒、感知有效、存在合法非零基础策略建议”的状态。仅用失败轨迹复现起点，随后由冻结的学习策略继续导航；只有完整安全到达的后续轨迹才考虑作为正来源，失败初始化片段不作为正确标签。不删停车原因、不强制最低速度、不放宽安全规则。

具体选择条件和两个起点见[来源协议](../parent_wait_protocol_20261016/PLAN.json)，当前收集状态见[来源结果](../parent_wait_source_20261016/RESULTS.json)。[完整诊断结果](RESULTS.json)保留每类输入的敏感性、停车原因分布和代表帧。

本审计固定原支持范围与硬掩码，只测试恢复头的信息使用。反事实输入可能不对应真实物理情形，既没有执行，也没有作为标签。输入敏感性不是正确解释、反事实安全性或新模型导航成功的证明。审计用时约 40 秒，平均 0.15 CPU 核，峰值 RSS 约 476 MiB。
